## Finding confirmation

Current behavior:

- `EditProfileScreen` pre-fills the name `Nastia`, never reads `profiles`, and closes without writing anything.
- Both profile photo surfaces present camera/library actions that only close or show temporary feedback. There is no picker dependency, bucket, object policy, upload/download path, image validation, or cleanup path.
- `ProfileScreen` reads stale signup metadata instead of the authoritative `profiles.display_name` row and always says the user is learning Tamil, even though learning language is per chat.
- The database already allows a user to update only their own `display_name`, `avatar_path`, and `interface_language`, but it does not validate profile values or protect a corresponding storage object namespace.
- The privacy policy and Play Data Safety draft say optional photos are collected, while the PRD simultaneously requires photo editing and lists real photo upload as a non-goal.

## Decision record

Required decision: Should the launch profile support only a real display name, or also collect and serve profile photos?

Options and tradeoffs:

- **Option A - display-name-only MVP (recommended):** persist a validated display name, render an initial avatar, remove every photo action, remove the false global `Learning Tamil` hint, and remove optional-photo claims from the privacy/Data Safety drafts. This closes every visible stub without adding media permissions, storage abuse risk, image moderation, or orphan cleanup. Photos can return as a separately designed post-launch feature.
- **Option B - full private profile photos:** implement display-name editing plus camera/gallery selection, bounded image processing, a private Supabase Storage bucket, member-scoped object reads, owner-only writes/removal, replacement cleanup, account-deletion cleanup, avatar rendering, and complete privacy/Data Safety disclosures. This preserves US-011 as written but materially expands security, moderation, dependency, release-permission, and manual-test scope.

Both options must:

- Make `profiles.display_name` the authoritative source across the profile, invites, chat lists, and partner headers.
- Trim and validate names server-side and client-side. Launch contract: 1-50 Unicode code points, no control characters.
- Remove the hard-coded profile-level language. Learning language remains a per-chat property; no global language is inferred without an approved selection rule.
- Show real save progress, server failures, and `Profile updated` only after a successful write.
- Preserve self-only profile updates and the L-08 member-only profile-read boundary.

Approved decision: **Option A - display-name-only MVP.** Persist a validated display name, keep initial avatars, remove all photo actions and photo-collection claims, and remove the false profile-level learning-language hint.
