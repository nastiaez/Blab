## Finding confirmation

Current behavior:

- `translate-message` accepts caller-supplied message text and language codes. It does not prove that the text belongs to a message the caller may read, that the requested target is the caller's selected learning language, or that the caller is an active account.
- Supabase JWT verification alone is not an application authorization boundary: the function does not resolve and require an authenticated user inside the handler.
- Any chat member may insert a shared `message_translations` row for any message in that chat. Because the client preserves the first insert, a member can poison the cache for the other participant.
- An edit deletes cached translations, but a request that started before the edit can still insert a stale result after the edit transaction.
- There is no per-account burst or daily translation quota. A caller can submit arbitrary text repeatedly and spend the shared OpenRouter balance.
- The removed portfolio demo has no current Flutter client, but its Edge Function remains in the repository and documents unauthenticated deployment with no quota.
- OpenRouter requests do not specify provider, data-collection, parameter-support, or Zero Data Retention routing requirements. OpenRouter therefore uses its default provider selection.
- The privacy policy names OpenRouter and OpenAI, but the current model has both first-party OpenAI and Microsoft Azure endpoints. Current OpenRouter documentation marks the Azure endpoint as zero retention and the first-party OpenAI endpoint as retaining prompts for an unknown period.

## Decision record

Required decisions:

1. What per-account quota should apply to uncached translation work?
2. May cache rows created under the old client-writable policy be retained?
3. Should translation use one disclosed ZDR provider or any provider OpenRouter currently classifies as ZDR-compatible?

Quota options:

- **Option A - bounded beta quota (recommended):** allow at most 60 uncached requests per minute, 200 uncached requests per UTC day, and 100,000 source characters per UTC day per account. Cache hits are free. This supports opening a 50-message page and normal beta use while bounding abuse. The app shows `Translation limit reached` when the durable quota rejects a request.
- **Option B - custom quota:** owner supplies different minute, daily request, and daily character limits. Higher limits improve heavy-use tolerance but increase the maximum shared-provider spend; lower limits can interrupt legitimate chat history translation.

Legacy-cache options:

- **Option A - invalidate old cache rows (recommended):** remove derived translation rows during migration, then regenerate them through the server-authoritative path as users view eligible messages. Message bodies are not removed. This is the only option that fully removes trust in values written under the old policy, at the cost of one-time translation latency and provider usage.
- **Option B - retain old cache rows:** backfill source hashes and trust existing values. This avoids regeneration cost but cannot prove that retained translations were not client-poisoned, so P1-08 remains only partially resolved.

Provider options:

- **Option A - Azure ZDR route (recommended):** keep `openai/gpt-4o-mini`, allow only OpenRouter's `azure` provider, require ZDR, deny data-collecting endpoints, and require support for all requested parameters. This gives a stable disclosed processor and excludes the currently non-ZDR first-party OpenAI endpoint. Availability is limited to Azure's eligible endpoints.
- **Option B - any eligible ZDR route:** require ZDR and deny data-collecting endpoints, but let OpenRouter select among all currently eligible providers. This improves provider flexibility but makes the downstream processor list dynamic and creates an ongoing disclosure/subprocessor review obligation.

Mandatory implementation boundaries independent of the options:

- The client sends only `messageId`; the server fetches the authoritative, non-deleted message after authenticating the user and checking active-account status, chat membership, translation cutoff, and the caller's selected target language.
- A durable, atomic database operation claims quota only for a cache miss.
- Only a trusted server path may write shared cache rows. Completion must compare the current message source hash so an edit cannot be followed by a stale cache insert.
- Existing authenticated cache inserts are revoked; members retain read access only for authorized chats.
- The unused public `translate-portfolio` function is retired and must be deleted from deployed environments during rollout.
- Provider/API errors returned to the app contain stable reason codes, not upstream response bodies or message content.

Approved decision: **Quota Option A + Legacy-cache Option A + Provider Option A.** Enforce 60 uncached requests per minute, 200 uncached requests and 100,000 source characters per UTC day per account; invalidate pre-L-13 derived cache rows; route `openai/gpt-4o-mini` only through eligible Azure ZDR endpoints with data collection denied.
