## Finding confirmation

Current behavior:

- `SupabaseConfig` embeds the production URL and publishable key and uses them
  as defaults. An ordinary `flutter run` therefore connects to production.
- An invalid `SUPABASE_PUBLISHABLE_KEY` override is silently rejected in favor
  of the production key, so a malformed local/staging command can unexpectedly
  operate on production.
- `scripts/local_test.sh` explicitly injects local Supabase values and is the
  only reliable development boundary today.
- The Supabase account has one active Blab project and no Blab staging project.
- Eight `supabase/.temp/*` CLI/link metadata files are tracked, including the
  production project ref and pooler URL.
- Sentry supports build-time DSN/environment values, but its environment
  defaults to `production` and the expected release define file is absent.
- Firebase Android configuration is gitignored and release builds require a
  file, but the repository has no environment-specific Firebase selection or
  cross-check against the selected app environment.
- Production is in `eu-west-1`; the tech spec currently claims Frankfurt
  `eu-central-1`. Both are EU regions, but the exact-region claim is wrong.

Evidence:

- Audit: `tasks/mvp-launch-audit-2026-07-15.md`, P1-12.
- Technical requirement: `tasks/tech-spec.md`, Backend conventions and Sentry
  configuration require one project/configuration per dev, staging, and prod.
- Client configuration: `lib/shared/data/supabase_config.dart`,
  `lib/shared/observability/observability.dart`, and `lib/main.dart`.
- Local/release tooling: `scripts/local_test.sh`, `docs/push-notifications.md`,
  `docs/play-listing.md`, Android Gradle configuration, and gitignore files.
- Deployed state verified on 2026-07-21 with the authenticated Supabase CLI:
  production project `bhzcexhebjszwyqvcsxs` is `ACTIVE_HEALTHY` in
  `eu-west-1`; all 29 repository migrations are applied with no local/remote
  gap; `delete-account` v6 and `translate-message` v9 are active with JWT
  verification; `send-push` v4 is active with webhook-secret authentication;
  expected OpenRouter/Firebase/webhook secret names are present. Secret values
  were not read.
- OpenRouter behavior was verified through synthetic requests: the configured
  key works, request-level ZDR/data-collection controls are applied, and the
  current `openai/gpt-4o-mini` route resolves to an eligible Azure endpoint.

## Decision record

Required decisions:

1. Does Blab create a separate hosted staging backend now, or revise the launch
   architecture to use local development plus production only?
2. Does Blab keep the healthy EU/Ireland production project for launch and
   correct the Frankfurt claim, or migrate production to Frankfurt before
   launch?

Options and tradeoffs:

- **Environment Option A - local + hosted staging + production (recommended):**
  create a new `Blab Staging` Supabase project, deploy migrations/functions
  through the same scripts, and require an explicit environment for every app
  run/build. This prevents development data and credentials from touching
  production and gives release candidates a realistic backend.
- **Environment Option B - local + production only:** remove the staging
  requirement from the tech spec and still make every production run explicit.
  This is cheaper and faster but production-only integrations cannot be tested
  safely before release.
- **Region Option A - keep `eu-west-1` for launch (recommended):** correct the
  exact-region documentation. Data remains stored in the EU and avoids a
  database/auth/function migration immediately before launch.
- **Region Option B - migrate to `eu-central-1`:** create a new production
  project and migrate schema, auth users/data, functions, secrets, OAuth,
  Firebase webhook configuration, and client builds. There are no launched
  users yet, but this materially expands L-18 risk and verification scope.

Approved decision: **Environment Option A + Region Option A.** Use local
Supabase for day-to-day development, create a separate hosted Blab staging
environment for realistic online testing, and reserve the existing project for
production. Keep production in `eu-west-1` for launch and correct the outdated
Frankfurt claim.

Approved by/date: `Aswin / 2026-07-21`

## Scope

In scope after approval:

- Replace production fallbacks with an explicit, validated environment
  contract for local, staging, and production app builds.
- Fail closed when URL/key/environment combinations are missing, malformed, or
  inconsistent; never fall back from local/staging to production.
- Add gitignored environment templates and reproducible run/build/deploy/verify
  commands that do not expose secret values.
- Remove tracked Supabase CLI link/temp metadata and ignore it going forward.
- Verify production migration/function/JWT/secret-name state against a checked
  manifest; add staging verification if Environment Option A is approved.
- Align Sentry and Firebase configuration checks with the selected environment.
- Correct directly affected technical documentation and record live evidence.

Out of scope:

- Rotating healthy secrets without evidence of exposure.
- Reading or committing secret values.
- Replacing Supabase, OpenRouter, Firebase, Sentry, or Vercel.
- Production data migration unless Region Option B is approved.
- Full CI implementation, which is owned by L-20.

Files/systems expected to change:

- Flutter environment configuration/bootstrap tests, Android release checks,
  local/release scripts, gitignore/config templates, Supabase deployment-state
  verification, launch records, and tech/setup documentation.
- Supabase staging project and provider configuration only if approved.

Migration, rollout, or rollback concerns:

- Existing production users/sessions must continue using the same project if
  Region Option A is selected.
- A release must fail before compilation/deployment if production inputs are
  absent; it must never substitute local or staging values.
- Environment files remain untracked. Publishable client identifiers may be
  public, but centralizing them as build inputs prevents accidental targeting.
- Rollback restores the previous app binary; server deployments remain
  independently versioned and verified.

## Test plan

Automated tests to add/update:

- Unit tests for environment parsing, required fields, URL/key consistency,
  and invalid-override failure behavior.
- Source/build contract tests for explicit production defines, ignored env and
  Supabase metadata, Firebase/Sentry requirements, and no embedded service key.
- Shell tests or dry-run assertions for local and deployed-state commands.

Required verification commands:

```bash
flutter analyze
flutter test
scripts/local_test.sh integration
flutter build appbundle --release --dart-define-from-file=<production-config>
supabase migration list --linked
supabase functions list --project-ref <production-ref>
supabase secrets list --project-ref <production-ref>
git diff --check
```

Manual prerequisites:

- Device/OS: emulator is sufficient for environment labeling and auth checks;
  final production binary remains part of the end-of-launch physical pass.
- Build/commit: L-18 candidate built once against staging and once against
  production configuration.
- Accounts/data: staging-only test account plus existing production test
  accounts; no cross-environment email/session assumptions.
- Network/environment: approved Supabase topology and owner-held provider
  credentials.

Manual test steps:

1. Run the local helper and sign in with a seeded account.
   Expected: the app reaches local Supabase only.
2. Run the staging build and create a staging-only account/message.
   Expected: no production account or message appears in either direction.
3. Run the production candidate and sign in with a production test account.
   Expected: production auth/chat/translation/push work and staging data is
   absent.
4. Attempt a run/build with a missing or malformed config.
   Expected: startup/build fails clearly before any backend request.

Regression checks:

1. Auth, invites, chat realtime, translation, account deletion, and push use
   the selected environment's services only.
2. Logs, generated artifacts, APK/AAB contents, and Git contain no service-role,
   OpenRouter, Firebase private key, webhook secret, or Sentry auth token.
