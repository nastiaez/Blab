# L-24: Repair Android warm invite-link routing

Status: `In progress`
Audit finding: `Follow-up`
Owner: `Aswin`
Recorded: `2026-09-14`
Last updated: `2026-09-22`

## Finding confirmation

Android delivered a warm `blab://i/<token>` intent to the running Blab
activity and `app_links` emitted it to Dart, but the app returned to `/chats`
instead of remaining on the invite resolver. The same link routed correctly
after a cold start.

## Root cause

Both Flutter's built-in deep-link handler and the `app_links` plugin handled
the same Android intent. The app-owned `app_links` route briefly opened the
invite resolver, then Flutter's competing handler replaced that route.

## Scope

- Make `app_links` the sole owner of Android initial and warm deep-link
  delivery.
- Preserve existing cold-start invite links and Supabase authentication links.
- Prove a warm custom-scheme invite leaves Chats and opens the invite resolver.

## Acceptance criteria

- [x] Android manifest disables Flutter's competing built-in deep-link handler.
- [x] A warm invite intent routes from Chats to the invite resolver in the

- [x] A cold invite intent still opens the invite resolver.
- [x] Automated regression protects the Android manifest contract.
