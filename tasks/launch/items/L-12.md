## Finding confirmation

Current behavior:

- The composer accepts 2,000 characters, but `translate-message` rejects text over 400 characters. Every message from 401 through 2,000 characters can be sent but always renders `Translation unavailable`.
- Every translation request declares the source language as English, including messages entered in another language.
- The implementation history defines an English-pivot model in which both people write English and each viewer receives a translation into their learning language.
- The input placeholder says `English or <learning language>`, while the PRD also describes incoming messages as authored in the partner's language. Those claims are not implemented by the English-pivot translator.
- Opening or rendering a chat requests missing translations even when `Show translations` is off. The toggle controls rendering only, not whether message text is sent to OpenRouter.
- Translation results are cached in Supabase and reused; L-11 prevents a language change from translating old history into the new language.

## Decision record

Required decisions:

1. Is launch translation explicitly English-pivot, or must it support messages authored in either English or the viewer's learning language?
2. Should the launch message limit remain 2,000 characters end to end, or should the composer be reduced to the translator's current 400-character limit?

Source-language options:

- **Option A — English-pivot MVP (recommended):** Both users write in English. Blab translates each eligible message into the viewer's selected learning language, renders that translation as the main bubble, and keeps the English original below it. Update the placeholder and product requirements so they do not claim arbitrary source-language input.
- **Option B — bilingual authoring:** Accept English or the selected learning language, detect which was entered, always render the learning-language text as the main bubble and English below it, and persist enough source/result metadata to reconstruct that display correctly. This is a wider protocol, cache-schema, rendering, and test change.

Length options:

- **Option 1 — retain 2,000 characters (recommended):** Raise the edge-function limit and output budget, keep the shared composer limit aligned, and verify a 2,000-character translation. This preserves the existing product requirement but increases worst-case latency and AI cost.
- **Option 2 — cap messages at 400 characters:** Lower the composer/database contract and update product requirements. This is cheaper and smaller but is restrictive for a messaging product.

Triggering behavior is not optional: `Show translations` must gate new AI requests as well as display. Cached translations may be loaded locally while hidden, but plaintext must not be sent to OpenRouter until the user enables translations.

Approved decision: **Source Option B + Length Option 1.** Accept English or the viewer's selected learning language. Normalize every successful result to learning-language main text plus English subtitle, and retain the existing 2,000-character composer limit end to end.

## Implementation record
