# L-09: Scope and deduplicate pending sends

Status: `Complete`

## Finding confirmation

Current behavior:

- Pending plaintext is stored at `pending_sends:<chatId>`, so two accounts using the same device and chat ID share one queue.
- The persisted local ID is not sent to PostgreSQL; each insert receives a new server-generated message ID.
- Manual retry removes the failed row and creates a new local ID.
- If PostgreSQL commits but the response is lost, retry inserts a duplicate message because neither client nor database can associate the attempts.
- Successfully delivered rows remain in the persisted pending queue indefinitely, even after the canonical row arrives through history or Realtime.
- Account deletion clears all pending keys, but ordinary logout relies on the unsafe unscoped key layout.

Evidence:

- Audit: `tasks/mvp-launch-audit-2026-07-15.md`, P1-10.
- Product requirement: `tasks/prd-blab.md:410-427` and FR-25/FR-26 require failed retry and offline auto-send behavior.
- Queue key and persistence: `lib/features/chat/state/pending_sends_state.dart:13-52`.
- Retry identity replacement: `lib/features/chat/state/chat_state.dart:152-167`.
- Server-generated insert identity: `lib/shared/services/chat_service.dart:80-93`.
- Account cleanup: `lib/shared/services/local_account_data_store.dart` and `lib/shared/services/supabase_auth_service.dart:88-98`.
- Deployed state: the existing `messages.id` UUID primary key can provide the server uniqueness boundary, but the current client does not supply it.

## Decision record

Required decision: `None.` Existing retry/offline requirements require account isolation and at-most-one logical message per queued send.

Options and tradeoffs:

- Use one client-generated UUID as the queue ID and `messages.id`. The existing primary key becomes the idempotency constraint, avoiding another public identifier and schema column.
- A separate `client_message_id` column and RPC would provide equivalent deduplication but adds schema/API surface without a distinct product need.

Approved decision: Reuse one client-generated UUID end to end, retain it for every retry, and accept an existing row only when sender, chat, and body match the original attempt.

Approved by/date: Existing approved product requirements, confirmed `2026-07-16`.

## Scope

In scope:

- Scope pending-send storage by authenticated user ID and chat ID.
- Reject and remove legacy unscoped queue payloads rather than assigning their plaintext to a later account.
- Persist owner metadata with each queue payload and validate it during hydration.
- Generate a standards-compliant random UUID once per composed message.
- Send that UUID as `messages.id`, preserve it through automatic/manual retries, and resolve duplicate-key responses only to an exact matching message.
- Reconcile canonical history/Realtime rows out of pending state and disk.
- Keep deletion cleanup compatible with all pending-send keys.
- Add unit and local integration coverage for account switching, legacy cleanup, retry identity, response-loss deduplication, and mismatched-ID rejection.

Out of scope:

- Connectivity reachability semantics and history/reconnect pagination, owned by L-16.
- Reply persistence, owned by L-10.
- Message UI redesign or notification delivery.
- Encrypting device-local pending plaintext; the approved launch model remains documented in L-00.

Files/systems expected to change:

- Pending-send state/storage, message send service/state, account identity provider, focused tests, and launch records.
- No new database column is expected because `messages.id` already enforces UUID uniqueness.

Migration, rollout, or rollback concerns:

- Legacy unscoped queues cannot be safely attributed and must be discarded.
- New clients remain compatible with existing rows and policies because callers already have insert permission on `messages.id`.
- Older clients remain functional but do not gain idempotency until updated.

## Implementation record

Summary:

- Pending queues now use `pending_sends:<userId>:<chatId>` plus an owner-validated payload envelope; unsafe legacy and mismatched payloads are deleted.
- Every composed message receives one cryptographically random UUID v4 that remains its queue ID, retry ID, and PostgreSQL `messages.id`.
- Duplicate inserts converge to the existing row only when authenticated sender, chat, body, and live-message state match; conflicting reuse is rejected.
- Failed-send retry keeps the original UUID, including when the first insert committed but its response was lost.
- Canonical history and Realtime rows reconcile delivered queue entries out of memory and disk.
- Hydration merges immediate in-memory sends with disk state, serialized writes cannot overwrite newer snapshots out of order, and delayed persistence no longer touches disposed Riverpod state.
- The debug failure control is one-shot and auto-disarms after creating a failed bubble, so its retry exercises the real send path deterministically.
- Failed bubbles now capture their full pointer surface and show a click cursor on desktop/web; normal delivered bubbles retain per-word dictionary taps.

Failure record, if any:

- Failed step: Retry the failed `L09 retry once` send after disabling simulated failures.
- Expected: The original queued message is delivered once and appears for Alice.
- Observed: The old message was not delivered.
- Reproduction evidence: Local PostgreSQL contained zero messages whose body starts with `L09` after the failed manual attempt, so no retry insert completed.
- Root cause: The debug failure control was persistent. A browser route reload reset it to off, so clicking the toggle while following the disable instruction could arm it again and force the retry to fail before reaching PostgreSQL.
- Fix: The debug control now fails one send and auto-disarms; the retry uses the real send path without another dev-menu transition.
- Failed step: Click the failed message in Flutter web to open Retry/Delete.
- Expected: Clicking anywhere in the failed bubble opens the failed-message sheet.
- Observed: Clicking the message text did nothing, leaving no accessible Retry action with a mouse.
- Root cause: `MessageText` gives translated words their own tap recognizers; those child recognizers won the gesture arena over the failed bubble's outer `onTap`.
- Fix: Failed bubbles now absorb child word pointers and route clicks from text or padding to Retry/Delete; non-failed bubbles keep dictionary word taps.
- Failed step: Receive the committed retry on an Android app process left alive overnight.
- Expected: Alice receives the message without restarting.
- Observed: The database held one correct Bob row, but Alice's open chat remained at yesterday's history until the app process restarted; after restart the chat list showed `Hallo Alice!` and one unread message.
- Reproduction evidence: Realtime logged a terminated/recreated replication connection and subscription-error activity; PostgREST logged statement timeouts; the Android process had remained alive since the prior day and logged session refreshes but no replacement message subscription.
- Classification: Existing L-16 reconnect/history defect. It did not duplicate or lose the L-09 send, and restart history recovered the durable row.
