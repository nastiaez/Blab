## Finding confirmation

Current behavior:

- Message bodies are stored as plaintext in Supabase Postgres.
- RLS controls database access, but Supabase infrastructure and privileged server operations can access plaintext.
- The `translate-message` Edge Function receives plaintext and forwards it to OpenRouter using `openai/gpt-4o-mini`.
- Translation results are stored in Supabase.
- The public privacy policy says this version is not end-to-end encrypted.

Conflicting objectives:

- The README calls E2EE a hard gate before any external tester.
- The PRD requires ciphertext-only storage and says server compute must never receive plaintext.
- The progress plan defers E2EE to v1.1 in favor of a faster plaintext MVP.
- The privacy policy and Play listing describe a launch without E2EE and with third-party AI translation.
- The tech spec says AI is out of scope and no LLM calls should exist.

## Data boundary today

```text
sender device
  -> Supabase messages.body (plaintext at rest)
  -> recipient device

message plaintext
  -> Supabase Edge Function
  -> OpenRouter-selected provider
  -> translation/tokens
  -> Supabase message_translations (plaintext at rest)
```

This is transport encryption plus server-side access control, not end-to-end encryption.

## Decision required

Choose one launch model. The choice controls later database, translation, privacy, consent, testing, and store-listing work.

### Option A: Plaintext MVP with disclosed server-side AI

**Recommended for the fastest credible MVP.**

Contract:

- Messages and translations remain plaintext in access-controlled Supabase storage.
- TLS protects data in transit and RLS limits normal client access.
- Translation sends message text to OpenRouter only under an explicitly defined user-facing trigger and disclosure.
- Blab makes no E2EE or `we cannot read your messages` claim.
- Translation authorization, rate limits, retention/routing controls, cache integrity, deletion, and provider disclosures become launch requirements.
- E2EE remains a future redesign, not a promised incremental switch.

Advantages:

- Smallest change from the implemented architecture.
- Preserves the current AI translation experience.
- Most realistic path to testing and launch without building a cryptographic device/key protocol.

Costs and risks:

- Supabase/server operators and AI providers can process message plaintext.
- A database or privileged-service compromise can expose message content.
- Privacy positioning must be narrower and completely explicit.
- Adding E2EE later requires data migration, key management, multi-device design, and translation redesign.

### Option B: E2EE messaging with explicit client export for AI translation

Contract:

- Normal message storage and delivery use a proven E2EE protocol; Supabase stores ciphertext.
- Translation is off until a user explicitly requests or enables it with informed disclosure.
- The client decrypts locally, then deliberately exports selected plaintext for translation.
- Server-side shared plaintext translation caches are removed or redesigned.
- Marketing must explain that E2EE protects normal delivery, but translated content is disclosed to the selected AI processors.

Advantages:

- Stronger protection for messages that are not translated.
- Can retain external AI quality for users who knowingly choose it.

Costs and risks:

- Large cryptographic, key-management, recovery, multi-device, migration, and UX project.
- Translation weakens the simple E2EE privacy story and needs precise consent/data-flow controls.
- Considerably delays external testing.
- Must use a proven messaging protocol/library; custom cryptography is not acceptable.

### Option C: E2EE messaging with on-device translation only

Contract:

- Messages remain ciphertext outside participant devices.
- Translation and word processing happen on-device; no plaintext is sent to Supabase compute, OpenRouter, or another cloud model.
- OpenRouter translation is removed from launch scope.

Advantages:

- Best alignment with the current privacy-first PRD.
- Cleanest defensible E2EE claim and smallest plaintext exposure boundary.

Costs and risks:

- Requires a suitable on-device model/dictionary strategy for every promised language pair.
- Download size, memory, latency, quality, device support, and model licensing need validation.
- Likely requires reducing initial language coverage or delaying launch.

## Recommendation

Approve **Option A** for a small external MVP if launch speed and translation are the priorities. Treat it as a deliberate security model, not as temporary E2EE-complete architecture. Before launch, make translation user-triggered or otherwise clearly disclosed, constrain OpenRouter provider retention/routing, secure the function and cache, complete deletion/moderation operations, and reconcile every E2EE statement.

Choose **Option B** only if E2EE is a non-negotiable product promise and external cloud translation remains essential. Choose **Option C** if the strongest privacy posture is more important than current translation breadth and launch timing.

## Scope

In scope:

- Select the launch data-protection and translation model.
- Record the plaintext boundary and permitted processors.
- Establish which product/privacy claims are allowed.
- Establish whether E2EE and AI translation are launch requirements or deferred work.

Out of scope:

- Implement encryption, translation changes, consent UI, policies, or migrations.
- Update public documents before the model is approved.
- Select specific cryptographic packages or on-device models.

Files/systems expected to change:

- This decision record and the launch backlog only.

Migration, rollout, or rollback concerns:

- Option A needs no immediate data migration but creates future E2EE migration work.
- Options B and C require a protocol, key lifecycle, plaintext-to-ciphertext migration, and backward-compatibility plan before external testing.

Approved decision: **Option A - Plaintext MVP with disclosed server-side AI.**

Approved boundaries:

- Supabase Postgres may store message bodies and translations as plaintext for this MVP.
- Supabase Edge Functions may receive plaintext to provide translation.
- OpenRouter and its selected model provider may process plaintext only for translation under the disclosure and controls implemented by downstream launch items.
- Blab must not claim this MVP is end-to-end encrypted or that its operators technically cannot read messages.
- TLS, RLS, least privilege, deletion, translation authorization, rate limiting, provider retention/routing controls, and accurate disclosures remain mandatory launch requirements.
