## Finding confirmation

Current behavior:

- Any authenticated account can select every row in `public.profiles`, despite the product being invite-only with no public profiles.
- A sender can update any column on their message at any time. The policy does not enforce chat membership, the 24-hour body-edit window, or immutable ownership and routing fields.
- A sender can physically delete their message through the API instead of using the product's reversible soft-delete flow.
- A read receipt validates only its claimed reader ID. It does not prove that the message belongs to the claimed chat, that the reader belongs to that chat, or that the reader is not acknowledging their own message.
- The `chat_list` security-invoker view relies on callers to filter `viewer_id`; a direct authenticated query returns both orientations of each shared chat.

Evidence:

- Audit: `tasks/mvp-launch-audit-2026-07-15.md`, P1-11.
- Product requirement: `README.md:15` says there are no public profiles; `tasks/prd-blab.md:280-291` defines a 24-hour edit window and unlimited sender deletion.
- Code/schema/config: `supabase/migrations/20260530000002_chat_rls.sql:7-12`, `supabase/migrations/20260716000002_moderation_operations.sql:451-462`, and `supabase/seed.sql:128-132` grant the broad behavior above.
- Client behavior: `lib/shared/services/chat_service.dart:95-135` writes read receipts and performs body edits and soft-delete toggles directly.
- Deployed state: migration `20260716000003` is applied to the linked Supabase project, linked migration history is aligned, and linked schema lint is clean.

## Decision record

Required decision: `None.` Existing product decisions already define private profiles, a 24-hour edit window, and sender deletion with no time limit.

Options and tradeoffs:

- Enforce message mutation shape in a database trigger while retaining the current client update API. This closes direct API bypasses without pulling L-10's reply persistence and edit-UI work into L-08.
- Replacing every mutation with security-definer RPCs would also work, but would enlarge the public API and duplicate L-10 client work without improving this item's observable boundary.

Approved decision: Use database policies, column grants, relational constraints, and a mutation trigger. Leave edit-action visibility and reply persistence to L-10.

Approved by/date: Existing approved product requirements, confirmed `2026-07-16`.

## Scope

In scope:

- Limit profile selection to the signed-in account and people who share a chat with it.
- Limit client profile updates to user-editable profile columns on the caller's own row.
- Enforce sender ownership, active membership, immutable message identity/routing fields, a 24-hour body-edit window, server-owned edit timestamps, and unlimited soft-delete/restore.
- Remove ordinary-client physical message deletion.
- Tie every read receipt to its real message/chat and require a different, authenticated chat member as the reader.
- Enforce the current account as `chat_list.viewer_id` inside the database view.
- Add local integration coverage for every allowed and denied boundary.

Out of scope:

- Hiding the Edit action after 24 hours and surfacing edit failures in the UI; L-10 owns the complete edit contract.
- Persisting replies; L-10 owns reply behavior.
- Message length, translation authorization, pagination, and pending-send idempotency.
- Public discovery or profile editing UI.

Files/systems expected to change:

- One Supabase migration, reproducible local grants in `supabase/seed.sql`, and a focused local Supabase integration test.
- Launch backlog and this work record.

Migration, rollout, or rollback concerns:

- Existing malformed read receipts must be removed before adding relational consistency constraints.
- The profile policy must continue to support the security-invoker `chat_list` view for real partners.
- The migration must be deployed before relying on these boundaries; rollback must not restore public profiles or hard deletes.

## Implementation record

Summary:

- Restricted profile selection to self and shared-chat partners and restricted profile updates to user-editable columns.
- Added immutable message fields, a database-owned 24-hour edit timestamp/window, unlimited server-timestamped soft delete/restore, sender/membership/suspension checks, and ordinary-client hard-delete denial.
- Added relational message/chat consistency and message/member/ownership validation for insert-only read receipts with a server-owned timestamp.
- Corrected `chat_list` so the view itself restricts rows to `auth.uid()` instead of trusting every caller to add a viewer filter.
- Updated the Flutter edit operation to let PostgreSQL own `edited_at`.
