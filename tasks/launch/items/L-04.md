## Finding confirmation

Current behavior:

- Release builds silently use the Android debug signing key whenever `android/key.properties` is absent.
- No upload keystore or signing properties are configured in this workspace.
- The repository and deployed Vercel association list only certificate fingerprint `E5:1F:...:71:0C`, recorded historically as a debug certificate.
- The audited fallback release used a different debug certificate, `98:EE:...:D7:AC`, so even the current sideloaded release cannot verify against the deployed association.
- The manifest correctly requests verification for `https://blab-gray.vercel.app/i/*`, and the live association is served directly over HTTPS with JSON content type and no redirect.

- Android guidance: `assetlinks.json` must contain the SHA-256 of the certificate signing the installed app; Play App Signing normally makes this different from a locally generated upload certificate
- Play guidance: Google signs delivered APKs with the app-signing key, while the developer signs the uploaded AAB with a distinct upload key

## Decision record

Required decision: `Confirm whether blab.nastia.ez already exists in Play Console with Play App Signing enabled, and whether an upload key already exists.`

Options and tradeoffs:

- Existing Play app and upload key: reuse them, verify their public fingerprints, and avoid breaking update continuity.
- Existing Play app without accessible upload key: create a replacement upload key and complete Play Console's upload-key reset process before building.
- New Play app with no key: generate a dedicated RSA upload key outside Git, back it up securely, upload the first AAB, let Play generate the recommended app-signing key, then publish both required public fingerprints.

Recommended decision: `For a new app, create a dedicated upload key, keep it outside the repository with an owner-controlled backup and passphrase, use Google-generated Play App Signing, fail release builds when upload signing is unavailable, and publish the Play app-signing fingerprint plus the upload fingerprint needed for direct release verification. Remove historical debug fingerprints from production association metadata.`

Approved decision: `Blab is a new Play app with no existing upload key. Generate a dedicated external upload key, use Google-generated Play App Signing, fail release builds closed, and publish only controlled upload/Play public certificate fingerprints.`

Approved by/date: `Aswin confirmed no existing Play app/build, 2026-07-16`

## Scope

In scope:

- Make release signing fail closed instead of silently producing a debug-signed release.
- Validate required signing properties without committing passwords or private keys.
- Generate or reuse an owner-approved upload key outside the repository and document secure backup ownership.
- Build an upload-signed release AAB and record its public SHA-256 certificate fingerprint.
- Enrol or confirm Play App Signing and record the Google-held app-signing SHA-256 fingerprint.
- Publish matching Digital Asset Links metadata on the invite host.
- Verify the deployed association and an installed Play-delivered build.

Out of scope:

- Migrating from `blab-gray.vercel.app` to a custom domain.
- iOS Universal Links.
- State-aware web invite rendering; tracked separately in launch documentation.
- Google OAuth certificate registration except where the same Play certificate must be recorded as a follow-up.
- Committing any keystore, password, service credential, or Play Console secret.

Files/systems expected to change:

- `android/app/build.gradle.kts`
- Signing setup template/verification scripts without secret values
- `web/.well-known/assetlinks.json`
- `docs/play-listing.md`
- Vercel deployment for `blab-gray.vercel.app`
- Play Console App integrity / internal testing state
- This work record and `tasks/launch/backlog.md`

Migration, rollout, or rollback concerns:

- If the package has ever been distributed, changing the app-signing key incorrectly can prevent updates. Existing Play state must be checked first.
- Removing a still-active certificate from `assetlinks.json` can break links for builds signed with that certificate; only owner-approved production and controlled-test certificates should remain.
- App Link verification is cached on devices. Manual verification must reset/re-request domain verification after deployment.
- Rollback to debug fallback is prohibited for launch artifacts.

Summary:

`blab.nastia.ez`. Android namespace/application ID, Kotlin source package,
Digital Asset Links metadata, Play listing URLs, contract tests, and current
launch instructions now use that identity consistently.

Release signing now fails closed and a dedicated external upload key signs the
generated AAB. The repository association trusts that controlled certificate
instead of either known debug certificate. Play's app-signing certificate must
be added after the first Play Console upload, before production verification.

Files/migrations/configuration changed:

- `android/app/build.gradle.kts`: release tasks now require complete, valid
  upload-signing configuration and never fall back to the debug certificate.
- `android/key.properties.example`: documents the local properties contract
  without containing credentials.
- `scripts/setup_android_signing.sh`: creates the one-time external upload key
  and gitignored local properties without printing its generated password.
- `web/.well-known/assetlinks.json`: replaces the historical debug certificate
  with the controlled upload certificate pending addition of Play's certificate.
- `web/.gitignore`: keeps Vercel's downloaded local environment file outside
  Git in addition to its project-link metadata.
- `test/android_release_contract_test.dart`: protects signing and App Link
  association invariants.
- `docs/play-listing.md`: documents owner backup and first-upload steps.

Security/privacy review:

- Upload and app-signing private keys are security credentials; only public certificate fingerprints belong in Git or website association metadata.
- A debug fallback makes a release artifact easy to misidentify and must be removed.

Operational or documentation changes:

- The refreshed Vercel session linked `web/` to the existing `getblab` project
  and deployed the controlled upload certificate to the production alias.
- The owner confirmed both generated signing files are backed up in 1Password
  and synchronized.
- The first internal-track upload must use Google-generated Play App Signing;
  its public app-signing SHA-256 must then be added to the association.
