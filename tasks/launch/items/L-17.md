## Finding confirmation

Current behavior:

- Blab receives messages only while the app can maintain or restore its Supabase connection. A backgrounded or stopped Android app receives no system notification.
- The Flutter project has no Firebase Core/Messaging dependency, notification-permission flow, token registration, foreground/background handler, or notification-tap routing.
- The Android app has no Firebase Gradle plugin, `google-services.json`, notification permission, notification channel, or notification metadata.
- Supabase has no private device-token table and no message/invite event pipeline that calls FCM.
- The product sources conflict: US-038, FR-29, and the tech spec require FCM, while the prototype non-goals and progress log defer actual push to v1.1.

## Decision record

Required decision: Does the Play Store MVP implement real Android push notifications, or is this release explicitly limited to a closed beta until push is implemented? If implemented, may Google process original message text for notification previews?

Options and tradeoffs:

- **Option A - Android FCM launch path (recommended):** Implement background notifications for new messages and successful invite claims. Ask permission only after the first chat opens, store per-account device tokens privately, send generic payloads without message plaintext, deep-link taps to the correct chat, and remove stale tokens. This makes the messaging MVP credible for general Play distribution but requires an owner-created Firebase project/configuration and server credential before end-to-end device verification.
- **Option B - closed-beta constraint:** Ship without push only to a named closed test cohort, remove or mark notification requirements and launch claims as deferred, and prevent the release package from being treated as the general-production MVP. This avoids Firebase work now but leaves L-17 intentionally unresolved for public launch and requires another implementation gate before production rollout.

Approved decision: **Option A - Android FCM launch path with message previews.** Notifications show the sender name and a truncated original-message preview when that device's preview setting is enabled; otherwise they use generic content. Translations are never included.

Approved by/date: `Aswin / 2026-07-20`

## Scope

In scope for Option A:

- Android notification permission after first chat open, including a once-dismissible denied reminder and a Profile link to Android notification settings.
- FCM token registration, refresh, account-switch/logout cleanup, and private server-side token storage.
- Generic background notifications for persisted new messages and successful invite claims, excluding the originating user/device.
- A per-device **Show message previews** preference. Enabled notifications may send the sender name and original message body through Google FCM; disabled notifications contain only generic Blab copy.
- Notification taps that open the intended chat after cold start, background resume, or authentication restoration.
- Idempotent delivery-event handling, stale-token cleanup, and non-blocking failure behavior so notification outages never fail message delivery.
- Firebase/Supabase setup documentation and local automated tests that do not commit credentials.

Out of scope:

- iOS/APNs support; the repository currently has no iOS target and Play Store launch is Android-only.
- Notification preferences beyond the preview toggle, per-chat mute, custom sounds, badges, rich content, or notification replies.
- Guaranteed exactly-once push display; FCM delivery is best effort, while database message delivery remains authoritative.
- Production credential creation/deployment, which requires owner-controlled Firebase and is finally verified in L-18.

Files/systems expected to change for Option A:

- Flutter dependencies/bootstrap, Android Gradle/manifest resources, chat/profile UI, routing, localization, notification service/state, Supabase migrations/functions/tests, and setup documentation.

Migration, rollout, or rollback concerns:

- Device tokens are sensitive routing identifiers: clients may write/delete only their own tokens and may not enumerate any tokens; only the service role may read them for delivery.
- FCM service-account material and `google-services.json` environment configuration must not be improvised or committed as secrets. Release builds must fail clearly when required production configuration is absent.
- When previews are enabled, Google FCM may process the original message body and sender display name for delivery. Payloads never include translations, email addresses, provider secrets, or extra learning data. When previews are disabled, payloads contain only generic copy and a chat identifier for authenticated in-app routing.
- Rollback may disable the server sender first, then remove client registration. Existing token rows must have a documented purge path.

Manual test steps for Option A:

1. Clean-install and sign in, then remain on the chat list.
   Expected: Android does not request notification permission.
2. Open the first chat.
   Expected: Android requests notification permission once, after the chat becomes available.
3. Grant permission, leave previews enabled, background and then swipe Blab away from Recents, and send a long message from the other account.
   Expected: A notification shows the sender and an Android-truncated original-message preview; no translation is present. The message itself remains delivered if FCM is delayed or unavailable.
4. Tap the notification from background and terminated states.
   Expected: Blab opens the correct authenticated chat exactly once.
5. Repeat from a clean install but deny permission, return to the chat, dismiss the inline reminder, and reopen the chat.
   Expected: The reminder appears once and stays dismissed; Profile opens Android notification settings.
6. Log out, sign in as another account on the same device, and send messages to both accounts.
   Expected: Only the active account receives notifications on that device; no token leaks across accounts.
7. Claim an invite while the inviter's app is backgrounded.
   Expected: The inviter receives a generic joined notification and tapping it opens the resulting chat.
8. Disable **Show message previews**, background Blab, and send another message.
   Expected: The notification uses generic Blab copy and exposes no sender or message content; re-enabling previews restores previews for later notifications.

Regression checks:

1. Foreground realtime messages still appear once with no duplicate system notification.
2. Notification delivery failures never roll back, duplicate, or mark a persisted message failed.
3. Message bodies and translations never appear in FCM request payloads or operational logs.

## Implementation record

Summary:

- Added Android FCM initialization, permission timing, token lifecycle, notification settings, and authenticated tap routing.
- Added private token storage, transactional message/invite outbox events, idempotent delivery records, and the `send-push` FCM HTTP v1 Edge Function.
- Message previews are bounded original text only; disabled previews and invite claims use generic copy. Translations are never included.

Files/migrations/configuration changed:

- Flutter notification gateway/state/repository, chat and profile UI, routing, localization, and gitignored `google-services.json` Firebase configuration.
- Android notification permission, channel, FCM metadata, and native settings bridge.
- `20260720000001_push_notifications.sql`, `20260720000002_push_notification_webhook.sql`, `send-push` Edge Function and contract tests, local integration tests, setup template/documentation, privacy policy, and Play Data Safety draft.

Security/privacy review:

- App roles cannot enumerate tokens, events, or delivery rows. Owner-scoped RPCs register and remove only the current device/account association; service operations use the service role.
- The outbox contains no message body. The Edge Function obtains original text only after claiming an event, logs neither text nor raw tokens, and stores only a SHA-256 token hash in delivery records.
- Preview-enabled message text is an explicitly approved expansion of the plaintext processor boundary to Google FCM and is disclosed in the privacy policy and Data Safety draft.

Operational or documentation changes:

- `docs/push-notifications.md` records Firebase app creation, Supabase secrets, encrypted Vault-backed asynchronous webhook setup, release defines, rollback, and physical verification. Production migrations, Edge Function secrets, Edge Function deployment, and Vault webhook configuration are complete.
