## Finding confirmation

Current behavior:

- The chat-list failure state renders `chatsAsync.error.toString()` in a
  monospace red panel. PostgREST, auth, network, and internal exception details
  can therefore be exposed to users.
- Android does not declare a backup policy. Auto Backup defaults to enabled and
  can include SharedPreferences containing account-scoped pending message text,
  privacy choices, notification settings, and cached interface language.
- The Android launcher label is the literal lowercase `blab`, while the product
  and Play listing name are `Blab`.
- `pubspec.yaml` declares the coherent first-release version `1.0.0+1`, and
  Gradle correctly sources `versionName`/`versionCode` from Flutter, but no
  contract test protects this release metadata.
- Supabase CLI 2.109.1 warns that `[inbucket]` is deprecated and generates
  `[local_smtp]` for new projects.
- Required authenticated table/view privileges are restored only by
  `supabase/seed.sql`. Hosted projects do not run seed data, so migration parity
  does not guarantee the same client privileges as a fresh local reset.
- The first L-18 integration run after a cold local reset encountered a
  Realtime timeout and a transient PostgREST 502 before warm retries passed.
  The local reset helper temporarily rewrites an untracked CLI Postgres-version
  file to avoid an incompatible image.

Evidence:

- Audit: `tasks/mvp-launch-audit-2026-07-15.md`, P2 quality and

- Product/store requirement: `docs/play-listing.md` names the app `Blab`.
- Raw error: `lib/features/chats/chats_screen.dart`, `_ErrorState`.

- Privileges: `supabase/seed.sql` contains the full authenticated DML grant set;

- Platform guidance: Android Auto Backup is enabled by default, and Android 12+
  may still perform device-to-device transfer when only `allowBackup=false` is
  set. Explicit extraction rules are needed to control both transfer modes:
  <https://developer.android.com/identity/data/autobackup>.

## Decision record

Required decision: What Android backup behavior should Blab permit at launch?

Options and tradeoffs:

- **Option A - disable app-data backup and transfer (recommended):** set
  `allowBackup=false` and explicitly exclude all app data from cloud backup and
  device-to-device transfer on supported Android versions. Chats, profile, and
  interface language are server-backed; users sign in again on a new device.
  This prevents queued plaintext, sessions, and privacy settings from being
  copied and has the smallest launch risk.
- **Option B - selective backup:** preserve only harmless local preferences and
  exclude sessions plus pending message text. SharedPreferences stores these
  values together at file granularity, so this requires splitting storage,
  maintaining version-specific backup rules, and testing restore/account-switch
  behavior. It improves device migration but materially expands the MVP change.

Approved decision: **Option A.** Disable all Android app-data cloud backup and
device transfer for launch. Users sign in again and rehydrate server-backed
data; pending plaintext, sessions, and local-only settings are not restored.

Approved by/date: `Aswin / 2026-07-22`

## Scope

In scope after approval:

- Replace user-visible raw chat-list errors with a localized stable message and
  explicit Retry action while retaining diagnostics in Sentry/debug logging.
- Apply the approved Android backup policy for Android 11 and lower and Android
  12 and higher.
- Use the `Blab` display name from an Android string resource and add release
  metadata contract coverage without changing package name `blab.nastia.ez`.
- Replace deprecated `[inbucket]` local configuration with `[local_smtp]`.
- Add an idempotent migration that declares the final authenticated table/view
  privileges required by the Flutter client; remove the duplicate client grant
  repair from local seed data.
- Make the local reset path and cold integration verification deterministic on
  the supported Supabase CLI/service versions.

Out of scope:

- Dependency upgrades and Kotlin built-in migration; these require a separate
  compatibility review.
- CI implementation, owned by L-20.
- Store graphics, reviewer credentials, Data Safety, and product-document
  reconciliation, owned by L-21/L-22.
- Play signing/App Links changes, owned by L-04.
- Changing the package name or migrating production user data.

Files/systems expected to change:

- Chat-list UI/localization tests, Android manifest/resources/backup rules,
  release contract tests, Supabase config/migration/seed, local test tooling,
  and launch documentation.

Migration, rollout, or rollback concerns:

- The grants migration must preserve current authorized operations and continue
  denying direct profile mutation, unrestricted message updates/deletes,
  translation writes, and non-member access.
- The migration must be applied to staging before production and verified with
  two-user allow/deny integration tests.
- Disabling backup affects only future backup/restore behavior; server data is
  unchanged. Rollback can restore selective backup in a later app release.
- Existing release version code must not be reused after any Play upload.

  bounded disposable probe before running tests instead of adding delays to the
  production chat path.
