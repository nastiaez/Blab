# L-11: Enforce one chat per participant pair

## Finding confirmation

Current behavior:

- Each successful `claim_invite` inserts a new `chats` row and two memberships, even when the inviter and claimant already share a chat.
- Two different valid invite tokens for the same pair can be claimed concurrently and create separate chats because token-level locking does not coordinate across the participant pair.
- Authenticated clients can no longer insert chats or memberships directly, so `claim_invite` is the only current product creation path.
- The removed development `pair_with_email` RPC attempted to reuse a chat but had no persistent uniqueness constraint and is no longer callable.
- Existing duplicate chats were observed during manual testing; no migration or canonical selection rule exists.

Evidence:

- Audit: `tasks/mvp-launch-audit-2026-07-15.md`, P1-05.
- Product/history: `tasks/progress.md`, Step 2.9 records the duplicate-chat defect, expected one-chat behavior, language-setting question, and existing-data requirement.
- Product requirements: `tasks/prd-blab.md`, US-008, US-024 through US-027, and FR-4 define the invite and claim flow but do not resolve re-invite language behavior.
- Creation boundary: `supabase/migrations/20260715000001_enforce_invite_membership.sql` removes direct inserts and the development pair RPC.
- Current claim function: `supabase/migrations/20260716000002_moderation_operations.sql:502-555` always creates a new chat.
- Deployed state: Remote duplicate count and exact data shape are not verified. Migration design must preserve history and fail safely on unsupported chat shapes.

## Decision record

Required decision:

1. When an existing pair accepts a new invite, should the explicit new language choices replace both members' current `learning_language` values?
2. Should existing duplicate pair chats be automatically merged into the oldest chat, preserving their messages and references, or left for manual operator cleanup?

Options and tradeoffs:

- **Option A — update languages and merge duplicates (recommended):** Reuse the oldest chat ID, move duplicate messages/read receipts and chat references into it, retain the most recently created duplicate's language choices during migration, and apply both newly selected languages on every later re-invite. This preserves all history, makes the invite choices truthful, and reaches one canonical tile without operator work.
- **Option B — preserve languages and merge duplicates:** Reuse/merge exactly as above, but leave existing membership languages unchanged on re-invite. This avoids a settings change but makes both invite language selections ineffective when the pair already knows each other.
- **Option C — prevent only future duplicates:** Add pair uniqueness and reuse going forward, but leave existing duplicate chats visible pending manual cleanup. This has the smallest migration but does not close the observed launch defect.

Approved decision: **Option A.** Reuse the oldest chat as canonical, merge exact-pair duplicates while preserving history and references, retain the most recent duplicate's language settings during migration, and apply both users' newly selected languages on every successful re-invite.

Approved by/date: `Aswin / 2026-07-17`

## Scope

In scope:

- Add a canonical sorted participant pair to pair chats and enforce uniqueness in PostgreSQL.
- Make `claim_invite` atomically create-or-reuse the pair chat across same-token and different-token races.
- Preserve account suspension, invite TTL/single-use, self-claim, membership-consent, and RLS behavior from L-01/L-07/L-08.
- Consume a successfully claimed re-invite and point `resulting_chat_id` to the canonical chat.
- Resolve existing exact-two-member duplicate chats according to the approved migration decision.
- Preserve messages, replies, translations, moderation references, invite references, and read receipts when consolidating.
- Add database and local integration coverage for first claim, sequential re-invite, concurrent different-token claims, and legacy duplicate consolidation.
- Start a new per-member translation era when a language changes so preserved history stays in English and does not fan out OpenRouter requests.

Out of scope:

- Group chats or chats with fewer/more than two members.
- Reopening a chat between blocked users; block/invite product behavior is a separate moderation decision.
- Changing invite expiry, single-use semantics, public landing behavior, or share URLs.
- Client UI redesign; the existing claim path already opens the returned chat ID.

Files/systems expected to change:

- One Supabase migration, database pgTAP/integration tests, focused service comments if needed, and launch records.

Migration, rollout, or rollback concerns:

- Duplicate consolidation changes chat foreign keys and must run transactionally with relevant constraints deferred.
- The oldest chat ID is the proposed canonical identity so existing routes and the earliest relationship remain stable.
- Duplicate messages retain IDs and timestamps; translations follow message IDs. Invite/report chat references and receipt chat IDs must be repointed before duplicate chats are deleted.
- Unsupported legacy chats that do not contain exactly two members must not be silently rewritten or deleted.
- Rollback after consolidation cannot recreate the former duplicate chat IDs without a backup; a pre-deployment database backup is required.

## Implementation record

Summary:

- Added a sorted participant-pair identity to direct chats and a database uniqueness constraint so one pair cannot acquire multiple canonical chats.
- Reworked `claim_invite` to serialize claims by participant pair, create or reuse the canonical chat, consume each successful invite, and apply both explicit language selections.
- Added a transactional migration operation that merges exact-pair legacy duplicates into the oldest chat while preserving history and dependent references.
- Added a protected per-member translation cutoff. Language changes hide translations on older messages and limit cache hydration/OpenRouter calls to messages sent afterward.

Files/migrations/configuration changed:

- `supabase/migrations/20260717000002_unique_pair_chats.sql`
- `supabase/tests/database/chat_pair_consolidation.test.sql`
- `supabase/tests/database/membership_consent.test.sql`
- `test/integration/local_chat_pair_uniqueness_test.dart`
- `test/message_translations_state_test.dart`
- `supabase/seed.sql`
- `scripts/local_test.sh`
- `lib/shared/services/chat_service.dart`
- Focused chat model, state, screen, and chat-list preview files.

Security/privacy review:

- Pair uniqueness is enforced in PostgreSQL, not only in the client.
- The consolidation function is unavailable to anonymous and authenticated clients; only `service_role` can execute it after migration.
- The existing authenticated-only invite claim boundary and direct chat/membership insert denial remain in place.
- A membership trigger prevents adding a user outside a chat's canonical pair.
- Authenticated clients can update only `learning_language`; the database owns `translation_cutoff_at` and advances it when the language actually changes.

Operational or documentation changes:

- Back up the production database before applying the migration because merged duplicate chat IDs cannot be reconstructed by rollback.
- Unsupported legacy chat shapes with other than exactly two members remain unchanged with null pair columns.
