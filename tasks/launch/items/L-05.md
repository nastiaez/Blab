## Finding confirmation

Current behavior:

- The Change password form validates three local fields, displays
  `Password updated`, and closes without calling Supabase.
- `SupabaseAuthService.updatePassword` performs a real server update but is
  only used by the password-recovery flow.
- The profile displays Change password for every provider even though a
  Google-only account has no current password to reauthenticate.
- Delete-account behavior already distinguishes password and Google-only
  identities through `hasPasswordIdentity`.

## Decision record

Required decision: `What should a Google-only user see instead of a current-password change flow?`

Options and tradeoffs:

- Hide Change password for Google-only users: accurately reflects available
  credentials and avoids silently creating a new password identity. This is
  the smallest launch-safe behavior but narrows the PRD's unconditional row.
- Show a read-only “Managed by Google” row: explicit but adds a settings row
  with no action.
- Implement “Set password” account linking: gives another login method but
  changes account-recovery/security behavior and needs a separately designed,
  verified flow.

Recommended decision: `Hide Change password for Google-only users. Keep it for email/password identities and require current-password reauthentication immediately before changing the credential. Treat password linking as post-MVP scope.`

Approved decision: `Hide Change password for Google-only accounts. Email/password identities retain the action and must reauthenticate immediately before the update. Password linking is post-MVP scope.`

Approved by/date: `Aswin, 2026-07-16 (option 1)`

## Scope

In scope:

- Call the server for password changes and only report success afterward.
- Reauthenticate an email/password user with the current password before the
  update.
- Surface invalid-current-password, weak/new-password, network, and server
  failures without closing the screen.
- Prevent duplicate submissions and navigation races while saving.
- Apply the approved Google-only profile/direct-route behavior.

Out of scope:

- Adding a password identity to Google-only accounts.
- Changing the existing email recovery-link flow.
- Global session revocation on other devices; Supabase's configured Auth
  semantics remain authoritative.
- Password-strength policy changes outside this form.

Files/systems expected to change:

- `lib/shared/services/supabase_auth_service.dart`
- `lib/shared/state/auth_state.dart`
- `lib/features/profile/change_password_screen.dart`
- `lib/features/profile/profile_screen.dart`
- Focused widget and local Auth integration tests
- This work record and `tasks/launch/backlog.md`

Migration, rollout, or rollback concerns:

- No database migration is required; Supabase Auth owns credentials.
- A successful reauthentication refreshes the session before the update.
- The old password must continue working after every failed attempt and stop
  working only after a confirmed successful update.

## Implementation record

Summary:

- Email/password changes now reauthenticate against Supabase immediately before
  updating the credential. UI success occurs only after the server responds;
  failures remain inline and busy state prevents duplicate/back actions.
- Google-only users no longer see Change password in Profile, and a defensive
  direct route exposes no password form or mutation action.

Files/migrations/configuration changed:

- `lib/shared/services/supabase_auth_service.dart`: adds reauthenticated change
  and password-change-specific safe error mapping.
- `lib/shared/state/auth_state.dart`: adds injectable provider-aware identity
  and password-change actions.
- `lib/features/profile/change_password_screen.dart`: performs the real async
  update with validation, busy, error, success, and direct-route states.
- `lib/features/profile/profile_screen.dart`: hides the action for Google-only
  users.
- `test/change_password_test.dart`: six focused validation/provider/UI tests.
- `test/integration/local_password_change_test.dart`: disposable-user Auth
  boundary test.
- `scripts/local_test.sh`: runs every opt-in local integration test.

Security/privacy review:

- Current and new passwords must stay in memory only and must never be logged,
  persisted, included in telemetry, or sent anywhere except Supabase Auth.

Operational or documentation changes:

- L-04 remains blocked on Google Play identity verification under an explicit
  owner-approved sequencing exception.
- No database or deployed-service change is required for L-05.
