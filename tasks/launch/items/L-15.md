## Finding confirmation

Current behavior:

- The auth and Profile surfaces offer 11 interface languages, but selecting one changes only the displayed language code/name. All menus, buttons, validation, errors, and accessibility labels remain English.
- `interfaceLanguageProvider` is in-memory and defaults to English on every process start. It neither reads nor writes `profiles.interface_language` or device storage.
- The same provider can retain one account's temporary selection when another account signs in during the same process. Account deletion invalidates it, but ordinary logout does not.
- Flutter has no localization delegates, supported locales, generated localization classes, or ARB resources. Approximately 286 user-facing string call sites would need classification and migration.
- Auth uses an auto-closing bottom sheet while Profile uses a separate Apply screen, despite the PRD claiming the same auto-saving picker.
- The translation contract deliberately stores an English subtitle and English word glosses. The PRD and tech spec instead claim that changing interface language immediately re-renders those translations without stale cache entries.
- `profiles.interface_language` exists and has a narrow self-update grant, but the app never uses it.

Evidence:

- Audit: `tasks/mvp-launch-audit-2026-07-15.md`, P1-02 and the objective-conflict table.
- Product requirements: `tasks/prd-blab.md`, US-005, FR-3, and the 11-language list.
- Technical claims: `tasks/tech-spec.md`, Internationalization and locked decision 14.
- Current state/UI: `lib/shared/state/interface_language.dart`, `lib/features/auth/auth_screen.dart`, `lib/features/auth/widgets/language_picker_sheet.dart`, and `lib/features/profile/interface_language_screen.dart`.
- App wiring: `lib/main.dart` has no locale/delegate configuration; `pubspec.yaml` has no `flutter_localizations` setup.
- Translation contract: `lib/shared/services/message_translator.dart`, `lib/shared/models/message_token.dart`, and `supabase/functions/translate-message/contract.ts` require English subtitles/glosses.
- Persistence: `public.profiles.interface_language` exists, but no Flutter service reads or writes it.
- Deployed state: not verified. L-18 owns final production migration/environment verification.

## Decision record

Required decision: Which interface languages will Blab truthfully support at Play Store MVP launch, and should chat learning aids remain English or follow that interface language?

Options and tradeoffs:

- **Option A - English-only launch (recommended):** remove both interface-language selectors and the Profile row, keep all app chrome in English, keep English translation subtitles/word glosses, revoke the unused client preference write, and update PRD/tech claims. The 11 learning languages remain unchanged because they are chat content, not interface localization. This is the smallest launch-safe option and avoids shipping unreviewed translations.
- **Option B - full 11-language localization:** add Flutter localization generation/delegates and reviewed ARB translations for every user-facing/error/accessibility string; persist the pre-auth choice locally and signed-in choice to the current profile; scope hydration across auth changes; and make layouts robust for every language. To preserve current PRD claims, also change the secure translation/cache contract so subtitles and word glosses are generated and cached by both learning language and interface language. This materially increases AI/cache migration, translation-review, QA, and launch scope.
- **Option C - reviewed language subset:** choose an explicit launch subset, expose only those interface languages, and implement the same persistence/localization discipline as Option B. English learning aids can remain English only if US-005 and the tech spec are explicitly changed; otherwise the translation/cache expansion is still required. This is less work than 11 languages but requires the owner to name the languages and provide or approve reviewed copy.

Approved decision: **Option C with English (`en`), Ukrainian (`uk`), German (`de`), and Spanish (`es`).** English is the default and safe fallback. Localize all app interface copy for these four reviewed launch locales and persist the choice per account. Messages may be authored in any language and always remain visible exactly as typed. The optional translation uses only the chat's learning language; the interface locale controls word definitions, never a full-message rewrite. The composer placeholder is the localized equivalent of "Message".

Approved by/date: `Aswin / 2026-07-18`

Approved scope extension: **Final message display matrix and writing correction.** A successful message shows the viewer's learning language on top and interface language below. If the author writes in neither selected language, that author keeps the exact original below. Clear mistakes in the author's learning language render as an inline strike-through correction plus localized explanation for that author only; recipients see clean corrected output. Matching learning/interface outputs are deduplicated. Exact authored text remains available through the icon-labeled message sheet. Approved and revised by Aswin on `2026-07-18` after scenario review.

## Scope

In scope:

- Implement or remove the interface-language promise according to the approved option.
- Keep interface language distinct from each chat's learning language.
- Eliminate process-only/account-leaking preference behavior.
- Reconcile directly affected PRD and technical claims.
- Implement the approved two-lane display matrix, third-language author exception, author-only correction markup, clean recipient output, and exact-original access.

Out of scope:

- Adding or removing chat learning languages.
- General writing lessons or generated replies.
- Localizing the external website/legal documents unless explicitly selected.
- General copywriting or visual redesign unrelated to localization fit.

Files/systems expected to change:

- Interface-language state, auth/profile surfaces, app locale configuration, and tests.
- Option A: remove selectors and narrow the unused profile grant.
- Options B/C: localization resources/tooling, profile/device persistence, auth lifecycle hydration, and potentially translation schema/function/cache behavior.
- `tasks/prd-blab.md`, `tasks/tech-spec.md`, directly conflicting current records, and this launch work item.

Migration, rollout, or rollback concerns:

- Option A should retain the dormant database column for compatibility but remove client writes; rollback can restore the UI only with real behavior.
- Options B/C need a safe fallback to English for missing/corrupt locale values and must not carry one account's preference into another account.
- Changing translation cache identity requires a migration and must not serve a gloss/subtitle in the wrong interface language.
- No machine-generated launch translation should be represented as reviewed without owner/language-review evidence.

## Implementation record

Summary:

- Added generated Flutter localization for reviewed English, German, Spanish, and Ukrainian interface copy, with English as the default and fallback.
- Persisted signed-out interface preference locally and signed-in preference on the current profile, with auth-transition isolation and self-only database writes.
- Kept exact authored text authoritative in the message row, chat-list preview, disabled/failure states, third-language author exception, and View original sheet.
- Added one server-verified interface-language output alongside the learning-language output in each locale cache row.
- Added localized generic composer placeholder text ("Message") without constraining or rewriting the language the user types.
- Recovered committed translation cache rows when an Edge Function response is lost, preventing a successful server translation from remaining permanently "unavailable" in the client.
- Corrected localized empty-chat copy so the generated `(language, name)` formatter receives its arguments in the declared order.
- Added `translation`, `correction`, and `none` learning-aid modes. Same-language corrections are minimal and shared as clean data; only the author UI renders inline strike-through marks and a confidence-labeled interface-language explanation.
- Implemented learning-language top lanes, interface-language bottom lanes, author third-language preservation, recipient-clean correction output, and duplicate-lane suppression.
- Added an inline error icon and isolated per-message Retry for retryable learning-aid failures.
- Added tap access to the message action sheet and an icon-labeled exact-original section without breaking tappable word definitions or existing long-press access.

Files/migrations/configuration changed:

- Added `l10n.yaml`, four ARB resources under `lib/l10n`, app localization delegates, and localized interface call sites.
- Updated interface-language state, profile persistence, auth hydration, local account storage, and Profile/auth language controls.
- Added `message_learning_content.dart` and updated chat bubbles, translation state, chat-list previews, and translation models/services.
- Added migrations `20260718000002_interface_localization.sql` through `20260718000006_invalidate_copied_interface_translations.sql`; updated the secure Edge Function contract and final shared locale cache identity.
- Updated Flutter, database, Edge Function, and integration tests plus PRD, tech spec, and progress records.

Security/privacy review:

- Interface preference remains self-only and account-scoped; cross-account writes are denied and logout/account switching clears the previous account's state.
- Exact authored text remains immutable and authorized in the message row; generated learning/interface lanes never overwrite it and View original reads only that source.
- Learning-aid cache identity includes message, learning language, and interface language because word glosses/explanations vary by interface locale; cache writes remain server-only.
- Translations, corrections, and `none` results are shared only with authorized chat members whose learning and interface locales match.
- The provider returns one learning-aid mode plus learning and interface full-message outputs in one bounded request; server validation requires exact interface-source preservation and matching output when learning/interface languages are identical.
- Arbitrary detected source languages use the constrained `other` marker instead of failing or inventing an unsupported language code.

Operational or documentation changes:

- Local launch scripts now fail before Flutter startup when local Supabase or its publishable key is unavailable, avoiding misleading sessions with nonfunctional persistence.
- PRD, tech spec, progress record, and this launch item now describe the authored-text-first behavior.
